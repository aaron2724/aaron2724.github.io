During an enterprise HR and payroll transformation, different applications held overlapping employee information. The migration involved data from Preceda, iChris and Oracle iHub, alongside workforce and payroll dependencies involving Kronos. The challenge was not just to move fields into a new system. It was to establish which differences were real errors, which were legitimate business rules, and which needed a decision from HR or Payroll before loading or approving data. Can we explain every material difference between the source, migration output and target record before it affects payroll or employment data? My role: Hands-on profiling, cleansing, reconciliation, exception investigation, file preparation, testing support and communication of findings to HR, Payroll and Technology stakeholders. I supported delivery as part of a wider team, rather than owning the entire transformation. 02 / Data understanding Multiple systems, different meanings Employee information needed to be reconciled across a range of domains. I worked with data including employee identifiers, employment status, cost centres, positions, work patterns, leave groups, salary or remuneration attributes, and payroll-related classifications. Technical risk Records that do not line up An identifier or field can be present in two extracts but represent different record timing, formatting or mapping conventions. Business risk False positives and missed issues Flagging every difference as an error creates unnecessary remediation; ignoring differences can leave incorrect target data. The analysis covered individual employee records and larger testing extracts. The 5,000+ employee population and 15,000+ row testing datasets represent different measures of scale and should not be interpreted as the number of detected errors. 03 / Analytical workflow From raw extracts to decisions Excel and Power Query supported repeatable comparisons. The sequence below illustrates how I moved from source data to a list of issues that could be investigated and acted on. 01 · Input Collect & profile Check keys, available fields, missing values and file structure. 02 · Prepare Clean & map Normalise comparable values and apply agreed business mappings. 03 · Analyse Reconcile Compare aligned records, flag field-level differences and group exceptions. 04 · Resolve Validate & retest Agree corrections with owners, prepare outputs and verify subsequent extracts. Why this mattered: repeatable checks enabled the team to distinguish widespread mapping patterns from isolated employee exceptions, and meant newly received files could be evaluated against comparable rules. 04 / Reconstructed example How a mismatch became an actionable exception Below is a fictional illustration of the employee-level validation approach. Pivots and grouped outputs enabled stakeholders to assess the pattern and scale of exception types rather than reviewing thousands of rows individually. 05 / Logic and quality control Making the checks repeatable The analytical work required more than a single lookup. Examples of the checks and decisions involved included: Stable comparison keys: use appropriate identifiers to align records, recognising that some systems format employee keys differently. Field-level checks: compare important attributes independently rather than relying solely on an overall record status. Business-rule review: distinguish allowed mappings from errors, especially for remuneration, leave and employment attributes. Exception grouping: summarise by field, reason or affected cohort so the correct business owner can investigate. Re-testing: compare new extracts or outputs after corrections to determine whether an issue remains. Illustrative decision logic Conceptual example, not production Power Query code IF records cannot be reliably matched: Flag = "Identity / key review" ELSE IF mapped source value equals target value: Flag = "Match" ELSE IF a documented business rule explains the difference: Flag = "Confirm accepted mapping" ELSE: Flag = "Investigate with field owner" This is a simplified explanation of the method, not a claim that a particular production rule or script was implemented in precisely this format. 06 / Tangible contribution What I produced and supported Reconciliation workbooks Excel and Power Query comparisons that surfaced source-to-target discrepancies for investigation. Exception summaries Mismatch pivots and issue categorisation to communicate where data failed checks and required a decision. Validated migration inputs Cleaned and mapped data prepared for bulk uploads and checked against target requirements. Testing and cutover support Analysis of load errors, payroll-cycle differences and post-migration discrepancies alongside stakeholders. Specific workstreams included employee data alignment, migration file checks and post-switch validation of fields such as remuneration and full-time-equivalent information. The exact proprietary file layouts and employee-level data remain excluded from this public case study. 07 / Outcome and evidence The improvement was in the quality of decisions The contribution was to make complex, fragmented source data more comparable, identify exceptions in a repeatable way, and give stakeholders clearer evidence for migration validation and remediation decisions. Supported outcomes: structured exception review, validated migration input preparation, investigation of load errors and better visibility of outstanding data issues across testing and readiness activities. What I am not claiming: I have not included an error-reduction percentage, hours saved, financial savings or a claim of zero payroll defects because those figures have not been verified.
